博士转码/转行：一次不那么成功的经验分享
PhD Career Transition: Lessons from an Unsuccessful Journey

写这篇的目的很简单：给未来想转码/转行的博士一个更真实的参照，个人经验仅供参考。

目前我的毕业论文要求已经满足，paper 也发够了。过去几年里，我大部分 AI 相关的合作、写作、实验和落地，基本都是靠 自学 + 自己找资源 + 自己把项目做出来。导师在 AI 方向上并不擅长，但我依然认为他是个好老板——至少在我求职、转型的阶段，他愿意给空间，不会用"必须做某某方向"把人锁死。

这半年找工暂时还完全没成功，我更想把自己踩过的坑写下来：让后来人少走弯路，更早建立适合工业界的能力结构。

一、找实习，找工作要趁早：投简历"量变出质变"

不要等到自己觉得"完美 match"才投，也别只投几十个最 match 的就收手。

也许业界大拿、hot PhD 可以这么做，但如果你跟我一样是普通 PhD，建议不要抱这种心态。

时间节奏：我个人建议 8 月开始冲刺投递到 10 月；年底节假日会明显放缓；圣诞之后再开启春招节奏。

现实原因：投简历本身很耗时间，HC 变化也快，越早开始越能让自己进入"面试—复盘—迭代"的正循环。

keyword matching 是必须做的，不要一份简历投几千遍，那真的杯水车薪。

二、内推 / refer/connect 必须做：别怕打扰

内推、refer、connect 不是"锦上添花"，而是很多人进入流程的关键一步。

我的做法很简单：白天工作间隙顺手在 LinkedIn 上发消息、加 connect、求 refer。

大部分华人其实都很愿意帮忙（至少我几乎没遇到负反馈）。

我后来还有一个更现实的体会：心态上不要把它当成"求人"，把它当成"信息交换 + 互相成就"。

用"销售"的角度看求职——你是在"卖自己"给 HR/团队。想清楚：

  • 你能解决什么问题？
  • 你能省谁的时间/钱/风险？
  • 你是什么"货"？最适合什么"摊位"？

在马路上追着人发传单，转化率很低；但如果你的摊位足够清晰、有特色，别人会主动停下来拿传单。

当你开始从 HR 的 KPI 角度思考，很多事情会出现新的转机。

三、刷题要趁早：保持手感，不要断

LeetCode 这件事，最折磨人的不是难，而是"停一阵子就忘"。

模板题型大概就 10–20 个，目标不是刷爆，而是 刷熟刷透刷到能背出来。

不要断：停一两个月，恢复手感往往要两周起步。

我的体验：半年大概做了 400–500 题，但后来才意识到——很多面试并不怎么考"纯题"，更多考 dive deep + system design。题目只是帮你在压力下保持基本盘。

四、今天的技术栈太大了：不可能"学几门课就转码"

SQL、database、LeetCode、kernel、系统设计、分布式、LLM serving……

现在的时代不可能像以前那样：上几门课就觉得自己"懂了"。你必须接受现实：

  • 要么选一个火热的大类，然后高效投入；
  • 要么就会被碎片化知识拖死。

我以前很喜欢看公开课，但说实话：课程很难跟上时代变化。实战永远是最好的老师。

更现实一点的比喻是：公开课像教你"开枪101"，而实战是给你一把自动步枪（GPT）然后把你丢进战场，让你自己活着出来。

在 vibe coding 时代，学习速度最快的方式通常不是啃书，而是：快速做东西 + 快速复盘。

同理，做项目也建议用"mini repo"方式：

先把项目跑通、理解整体框架；遇到不懂的就往后翻、再回头看。很多时候等你回头，项目已经做完了，code 也理解了，技术栈也学得差不多了。

用 vibe coding / 第一性原理学习：问到自己问不出问题为止，这比"看完一门课"有效得多。

LeetCode 的价值不是"刷题"，而是：做过项目后你才知道它在训练什么

LeetCode 真正训练的是三件事：

  1. 边界/约束意识：不会因为 corner case 翻车
  2. 抽象能力：快速把问题变成可操作的pipeline
  3. 稳定性：压力下依旧保持水平的测试

四点五、Mock 面试非常有用

即使现在 AI 的效果非常好了，但是真人的 mock interview 的感受是完全不一样的。如果有条件的情况下花点钱，不管是现在比较火的一些 interview 准备网站也好，还是 system design 也好，稍微花点钱事倍功半的效果是非常显著的。

因为很多人面试机会有限，所以还是尽可能的抓住机会比较好。

五、我大量面试后才真正明白：0→1 和 1→1000 是两套能力体系

读博士更像 0→1：定义问题、搭系统、做实验、讲故事，把未知变成可发表的结论。

做新产品开发也更像 0→1：从需求到原型到上线，先把闭环跑起来就算成功。

但大厂的 infra / 平台工程对应的是 1→1000：

不是把功能"做出来"，而是让它 可复用、可审计、可灰度、可回滚、可观测、可维护、能抗峰值、能被别人接手。

说人话就是：微信一个人用，只是聊天工具；14 亿人用，你要解决的是"系统不崩、持续迭代、可观测、可回滚、可维护"。

我在传统硬件公司其实也经历过类似的事情，只是过去没系统学过那套"工程话术"，所以在 system design 面试里讲不出来细节。很多博士不是没做过，而是没学会用大厂能评估的方式表达：trade-offs、contracts、metrics、failure modes、rollout。

以及我后来发现：很多人其实不需要"从零开始"。在自己原有项目上，补上几个关键工程模块（比如数据契约、监控告警、灰度回滚、压测与容量规划），再把它跑通成一个 mini repo，就已经能把 0→1 的项目"翻译"成 1→1000 的叙事。

顺带一提，这也是为什么统计/数学背景的 PhD 往 quant 或 data scientist 转型的成功率往往更高：他们更习惯用数据口径、实验设计、指标解释来表达自己的工作成果——这套表达在工业界天然更容易对齐。

六、在聊技术的时候不要做产品经理

我个人有多年创业/产品视角，习惯从"用户/销售/产品"角度思考问题。这个思维在很多场景很有价值，但在某些美国 tech lead 的技术面里，反而会导致 vibe 对不上：对方要你讲"contracts / metrics / failure modes / rollout"，你讲成了"需求与商业价值"。

技术面最重要的是：先回答问题，再扩展视角，否则很容易发散、答非所问。business impact 很重要，但在 infra / system design 面试中，它更多是背景动机而不是核心。核心还是：系统是否能规模化落地、是否可维护、是否可监控、是否能稳定迭代。

七、最后一句：转码要趁早，别被学术路径绑架

这句可能有点刺，但我是真心的：转码要趁早。与其说转码，不如说，如果你想做 1-1000，就转 engineer，不管是 data engineer, AI engineer, infra engineer。Engineer 是一门复杂的学问，是要下苦工的。

别只听"发 paper 就够了"。paper 能发 AI 就发 AI，不让发就挂 arXiv。学术体系的激励、就业市场的现实、以及未来几年的人口趋势摆在那儿——你要为自己的人生负责。

当然，如果你喜欢做 0-1 的开放问题，喜欢创新，喜欢研究别人没研究过的东西，享受那种日日夜夜挑灯夜战然后自我突破的学术环境，那教职是非常好的。想清楚自己要的是哪一种人生，落子无悔。

八、我最感谢的一件事：华人社区的互相帮助，开放，包容，以及 AI infra 社区

这一路上帮助过我的人很多：完全不认识的同学之间的内推，老同学的搭把手，LinkedIn 内推、找工建议、经验分享……我都很感激。

我最近学的基本都是 LLM / serving / infra。打个广告并且非常感谢 SGLang 团队尤其是几位对外的负责人的包容性，也感谢社区维护者写了大量 blog 和实践经验——这是我见过社区维护比较好的之一。对很多"背景不完美、但愿意投入"的人来说，这种开放性非常珍贵。

九、但我也必须承认：我实力不济，这半年没转成功

该补的短板确实不少：无论是 system design、LeetCode，还是一些更偏工程化的表达方式，我都还在补课阶段。再加上每周一两个面试，白天还得 PhD 正常工作，长期下来精力被不断切碎，确实没能完成期待的目标。

最痛的不是失败，而是你以为自己准备对了，却发现面试在考另一套体系——比如准备 Python 结果要求必须 C++，准备 coding 结果只考 SD，准备 SD 结果全程考 domain knowledge，然后你开始怀疑自己是不是不适合。有时候别太否定自己，失败是常态，一直失败更是常态，大部分论文也都是需要无数次打磨才能发表到好的 journal 上的，这一点我相信大部分 PhD 应该都是可以苦中作乐的哈哈

这些都是我当下的理解，可能不完整也可能有偏差。欢迎批评指正和补充交流，我会认真吸收，也希望后来人少踩坑。谨以此贴，记录我不那么成功的转码路。

结语

中文：希望这篇文章能为正在考虑转码或转行的 PhD 朋友们提供一些参考。记住，每个人的路径都不同，重要的是找到适合自己的方向，并为之持续努力。

English: I hope this article can provide some reference for PhD friends considering a transition to coding or tech careers. Remember, everyone's path is different. What matters is finding the direction that suits you and persistently working toward it.
